# 3. Star schema (dimensional modeling)

A star schema puts the **measurements** of a business process in a fact table, and the **context** for those measurements in dimension tables around it. It is optimized for one thing: answering business questions simply and fast. It remains the best-supported shape for BI tools, Databricks SQL, and semantic layers such as Unity Catalog metric views.

```
                     dim_date
                        │
  dim_customer ── fact_ticket_sales ── dim_event
  (SCD Type 2)                         (SCD Type 1)
```

## The four-step design process

Ralph Kimball's process still works and is worth following in order:

1. **Choose the business process.** Ticket sales, not "the orders table". A process produces measurements.
2. **Declare the grain.** One row per order. Write it down; every later decision is checked against it.
3. **Identify the dimensions.** Who (customer), what (event), when (date). Each must have a single value per fact row at that grain.
4. **Identify the facts.** Quantity, unit price, gross amount: numbers that are true at the declared grain.

## Fact tables

| Type | Grain | Example | Updates |
|---|---|---|---|
| **Transaction** | One row per event | One row per order | Insert; optionally update status |
| **Periodic snapshot** | One row per entity per period | Tickets remaining per event per day | Insert per period |
| **Accumulating snapshot** | One row per process instance, with milestone dates | Order: placed, paid, refunded dates | Updated as milestones happen |
| **Factless** | One row per occurrence, no measures | Customer viewed event page | Insert |

`fact_ticket_sales` is a transaction fact that carries the order's current status, a common pragmatic choice. If you need to report how statuses changed over time, add an accumulating snapshot or a status-change fact instead of overloading this one.

Facts should be **additive** where possible (`gross_amount` sums across every dimension). Store the price actually paid on the fact: `dim_event.base_price` changes, but a sale's price never does. The playground's *Price increase* event demonstrates this.

## Dimensions

Good dimensions are wide, descriptive and full of the words people use in reports.

- **Surrogate keys.** `customer_sk` is a meaningless integer, one per dimension row. On Databricks use `BIGINT GENERATED BY DEFAULT AS IDENTITY`, which also lets you insert the `-1` Unknown member explicitly.
- **Unknown members.** A `-1` row in every dimension means a fact can always be loaded, even when its customer has not arrived yet. When the customer arrives, the fact is re-pointed. Try *Early-arriving fact* in the playground.
- **Degenerate dimensions.** `order_id` lives on the fact table with no dimension of its own.
- **Role-playing dimensions.** One `dim_date` joined as order date, event date and refund date, through views or aliases.
- **Junk dimensions.** Low-cardinality flags (channel, payment type) combined into one small dimension instead of cluttering the fact.
- **Conformed dimensions.** One `dim_customer` shared by every fact table that mentions customers. Plan them with a **bus matrix**:

| Business process | dim_date | dim_customer | dim_event | dim_venue |
|---|---|---|---|---|
| Ticket sales | ✓ | ✓ | ✓ | ✓ |
| Refunds | ✓ | ✓ | ✓ | |
| Event inventory | ✓ | | ✓ | ✓ |

## Slowly changing dimensions

`dim_customer` mixes types, which is normal:

- `city`, `country`, `loyalty_tier`: **Type 2.** A change closes the current version (`valid_to`, `is_current = false`) and inserts a new one.
- `full_name`, `email`: **Type 1.** Overwritten on every version.

Facts join to the version valid when they happened:

```sql
LEFT JOIN gold.dim_customer c
  ON c.customer_id = o.customer_id
 AND o.order_ts >= c.valid_from AND o.order_ts < c.valid_to
```

Two details matter in production:

- **The first version starts at the beginning of time** (`1900-01-01`), not at the customer's first `updated_at`. Otherwise an order placed before the customer record's timestamp, which happens with early-arriving facts, matches nothing.
- **Use half-open intervals** (`>= valid_from AND < valid_to`) so a timestamp matches exactly one version.

### Three ways to load SCD Type 2 on Databricks

1. **The classic MERGE.** Compare incoming rows with the current version, close changed versions and insert new ones (usually with a `UNION ALL` trick so one MERGE does both). Simple, but only correct when changes arrive in order.
2. **Rebuild versions from the change history, then MERGE** (used in `notebooks/03_gold_star_schema.sql`). Window functions derive every version from Silver's full change history in business time; a MERGE on `(customer_id, valid_from)` applies the differences. Late changes land in the middle of history correctly, and existing surrogate keys never change.
3. **`AUTO CDC ... STORED AS SCD TYPE 2`** in a declarative pipeline (`pipelines/medallion_pipeline.sql`). Databricks handles sequencing, out-of-order data and the `__START_AT`/`__END_AT` columns. Use `TRACK HISTORY ON * EXCEPT (...)` to keep Type 1 columns out of the history.

For new pipelines, prefer option 3. Option 2 is the right choice when you need full control in notebooks or jobs.

## Late-arriving data

- **Late-arriving dimension change** (a move that happened last week arrives today): insert it into history in business-time order. Facts in the affected window must be re-pointed; re-deriving the fact keys, as the notebook does, handles this.
- **Early-arriving fact** (an order before its customer): point it to the Unknown member, then re-point it when the customer arrives. Some teams insert an *inferred member* instead: a placeholder dimension row with the business key and empty attributes, filled in later.

## Snowflakes and one big table

- **Snowflaking** (normalizing dimensions into sub-dimensions) saves little storage on Delta and makes every query more complex. Avoid it unless a sub-dimension is genuinely shared and large.
- **One big table (OBT)** pre-joins facts and dimensions into one wide table. It is excellent as a *Gold product built from a star schema* for a specific dashboard. It is a poor *replacement* for the star schema: every new question needs another wide table, and their numbers drift apart.

## On Databricks

```sql
CREATE TABLE gold.fact_ticket_sales (
  order_id     STRING NOT NULL,
  date_key     INT    NOT NULL,
  customer_sk  BIGINT NOT NULL,
  event_sk     BIGINT NOT NULL,
  quantity     INT,
  unit_price   DECIMAL(10,2),
  gross_amount DECIMAL(12,2),
  order_status STRING,
  CONSTRAINT fact_ticket_sales_pk PRIMARY KEY (order_id) RELY,
  CONSTRAINT fact_ticket_sales_customer_fk FOREIGN KEY (customer_sk) REFERENCES gold.dim_customer
) CLUSTER BY (date_key, event_sk);
```

- **Primary and foreign keys are informational.** They are not enforced, so test them (`notebooks/06_validate.sql`). `RELY` tells the optimizer it may trust a primary key, which enables optimizations such as join elimination; only use it when your tests guarantee uniqueness.
- **Liquid clustering** (`CLUSTER BY`) replaces partitioning and Z-ordering for most tables. Cluster facts by the columns people filter on (date, event); cluster dimensions by their business key. `CLUSTER BY AUTO` lets Databricks choose, with predictive optimization enabled.
- **Comments** on tables and columns show up in Catalog Explorer and help AI-assisted querying. Write them for consumers.
- **Metric views** in Unity Catalog can define measures (revenue, tickets) once on top of the star schema, so every dashboard computes them the same way.

## When the star schema is the right choice

- Analysts, dashboards and BI tools are the main consumers.
- A domain has a manageable number of sources, or integration happens upstream.
- You can define the business processes and their grain.

It struggles when dozens of overlapping sources change shape constantly, or when you must reproduce exactly what every source said at every point in time. That is where the next chapter comes in.
