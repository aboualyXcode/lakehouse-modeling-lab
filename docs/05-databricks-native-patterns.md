# 5. Databricks-native modeling patterns

The modeling ideas in chapters 3 and 4 are decades old. What changes on Databricks is *how* you implement them: Delta Lake gives you ACID tables with `MERGE`, Unity Catalog gives you governance and constraints, and declarative pipelines take over much of the incremental-loading work that used to be hand-written.

Product names change; this chapter uses the names in the Databricks documentation as of 2026 and mentions the older ones you will still see in blogs and code.

## Unity Catalog: the namespace is part of the model

`catalog.schema.table` is the first modeling decision. Decide it once, write it down, and apply it everywhere (see [chapter 2](02-medallion-architecture.md#organizing-it-in-unity-catalog)).

- **Separate environments by catalog** (`dev`, `prod`), not by table name suffix.
- **Use schemas for layers and domains**, and grant privileges at schema level.
- **Put files in volumes** (`/Volumes/<catalog>/<schema>/<volume>/…`), not in arbitrary cloud paths, so access is governed like tables.
- **Write comments and tags.** Table and column comments appear in Catalog Explorer, lineage and AI-assisted tools. Tags (for example `pii = true`) drive governance policies.

## Delta Lake features that change modeling

| Feature | What it gives a model |
|---|---|
| **`MERGE INTO`** | Upserts, SCD Type 1 and 2, insert-only loads with `WHEN NOT MATCHED`, and cleanup with `WHEN NOT MATCHED BY SOURCE`. The workhorse of every notebook here. |
| **Change data feed** | Row-level changes of a Delta table, so downstream layers can process only what changed. |
| **Time travel** | Query or restore a table as of an earlier version. Useful for audits and recovering from a bad load; not a substitute for modeled history (retention is limited). |
| **Liquid clustering** | `CLUSTER BY (cols)` organizes data for the columns you filter and join on, and can change later without rewriting the table. Replaces partitioning and Z-order for most tables. `CLUSTER BY AUTO` lets Databricks choose. |
| **Deletion vectors** | Make `MERGE`, `UPDATE` and `DELETE` cheaper by marking rows instead of rewriting files. On by default for new tables in recent runtimes. |
| **Predictive optimization** | Runs `OPTIMIZE` and `VACUUM` for managed tables automatically. |

## Keys and constraints

```sql
customer_sk BIGINT GENERATED BY DEFAULT AS IDENTITY (START WITH 1)
CONSTRAINT dim_customer_pk PRIMARY KEY (customer_sk) RELY
CONSTRAINT fact_customer_fk FOREIGN KEY (customer_sk) REFERENCES gold.dim_customer
```

- **Identity columns** generate surrogate keys. `BY DEFAULT` allows inserting explicit values such as the `-1` Unknown member; `ALWAYS` forbids it. Identity values are unique but not guaranteed to be consecutive, and writes to a table with an identity column cannot run concurrently, so keep one writer per dimension.
- **Hash keys** (`md5`, `sha2`) are the alternative when several writers must generate keys independently, which is why Data Vault uses them. `xxhash64` gives a compact `BIGINT` key in declarative pipelines, where identity columns are not available on materialized views.
- **Primary and foreign keys are informational.** Databricks does not enforce them, but they document the model, BI tools use them to build joins, and `RELY` lets the optimizer use a primary key for optimizations such as removing unnecessary joins. Only declare `RELY` when your tests guarantee the constraint holds.
- **`NOT NULL` and `CHECK` constraints are enforced.** Use them for rules that must never be broken.

## Ingestion: Auto Loader and `read_files`

```python
(spark.readStream.format("cloudFiles")
    .option("cloudFiles.format", "json")
    .schema(EXPECTED_SCHEMA)
    .option("rescuedDataColumn", "_rescued_data")
    .load(landing_path)
    ...
    .writeStream.option("checkpointLocation", checkpoint)
    .trigger(availableNow=True)
    .toTable("bronze.orders"))
```

- **Auto Loader** (`cloudFiles`) ingests new files exactly once, tracked by the checkpoint. `trigger(availableNow=True)` turns a stream into an incremental batch job.
- **Pin the schema and keep a rescued data column** in Bronze. New or malformed fields are captured instead of failing the load or disappearing. Alternatively, let Auto Loader infer and evolve the schema with `cloudFiles.schemaLocation` and a `schemaEvolutionMode`.
- **`read_files`** is the SQL equivalent, used in declarative pipelines: `FROM STREAM read_files('/Volumes/…', format => 'json', schema => '…')`.
- **Lakeflow Connect** provides managed connectors for databases and SaaS applications, and can deliver CDC directly.

## Declarative pipelines

Lakeflow pipelines, introduced as Delta Live Tables and later named Lakeflow Spark Declarative Pipelines, let you declare datasets instead of orchestrating steps. `pipelines/medallion_pipeline.sql` implements this repository's whole Medallion flow that way.

| Object | Use for |
|---|---|
| **Streaming table** | Append-mostly data processed incrementally: Bronze, Silver change history, AUTO CDC targets. |
| **Materialized view** | Results of a query, refreshed incrementally where possible: Gold facts, dimensions and aggregates. |
| **View** | Intermediate logic that does not need storing. |
| **Expectation** | A data-quality rule on a dataset: record violations, drop the row, or fail the update. |
| **Flow** | How data reaches a target, including `AUTO CDC`. |

### Expectations

```sql
CREATE OR REFRESH STREAMING TABLE silver_order_changes (
  CONSTRAINT has_customer      EXPECT (customer_id IS NOT NULL) ON VIOLATION DROP ROW,
  CONSTRAINT positive_quantity EXPECT (quantity > 0)            ON VIOLATION DROP ROW
) AS SELECT ... FROM STREAM(bronze_orders);
```

Violations are counted in the pipeline's event log, so data quality becomes observable. Use `ON VIOLATION FAIL UPDATE` for rules where a bad row must stop everything, and a plain `EXPECT` to only record. When you need the rejected rows themselves, route them to a quarantine table with the inverse condition, as `notebooks/02_silver_conform.sql` does.

### AUTO CDC: SCD Type 1 and 2 in one statement

```sql
CREATE OR REFRESH STREAMING TABLE dim_customer_history;

CREATE FLOW dim_customer_scd2 AS AUTO CDC INTO dim_customer_history
FROM STREAM(silver_customer_changes)
KEYS (customer_id)
SEQUENCE BY updated_at
COLUMNS * EXCEPT (updated_at)
STORED AS SCD TYPE 2
TRACK HISTORY ON * EXCEPT (full_name, email);
```

- `SEQUENCE BY` orders changes by business time, so out-of-order data is applied correctly. Use `STRUCT(ts, id)` to break ties.
- `STORED AS SCD TYPE 2` maintains `__START_AT` and `__END_AT`; `TRACK HISTORY ON * EXCEPT (...)` keeps Type 1 columns out of the history.
- `APPLY AS DELETE WHEN op = 'DELETE'` handles deletes.
- `AUTO CDC FROM SNAPSHOT` derives changes when a source only provides full snapshots.
- `AUTO CDC` replaces the older `APPLY CHANGES INTO` syntax, which still works.

The same in Python:

```python
from pyspark import pipelines as dp
from pyspark.sql.functions import col

dp.create_streaming_table("dim_customer_history")
dp.create_auto_cdc_flow(
    target="dim_customer_history",
    source="silver_customer_changes",
    keys=["customer_id"],
    sequence_by=col("updated_at"),
    except_column_list=["updated_at"],
    stored_as_scd_type=2,
    track_history_except_column_list=["full_name", "email"],
)
```

## Data Vault on Databricks

- Load hubs and links with `MERGE ... WHEN NOT MATCHED THEN INSERT`: idempotent and insert-only.
- Load satellites with the business-time comparison from [chapter 4](04-data-vault-2.md#the-out-of-order-pitfall).
- Cluster hubs and links by hash key, and satellites by `(hash key, applied_ts)`.
- Hash keys as `STRING` are readable; `BINARY` (`unhex(md5(...))`) halves storage on very large vaults.
- Generate loads from metadata. Declarative pipelines can host the business vault as views and materialized views.

## Star schemas on Databricks

- Facts and dimensions as managed Delta tables, or as materialized views in a pipeline.
- Identity surrogate keys, `-1` Unknown members, informational keys with `RELY`, and liquid clustering on join and filter columns.
- **Metric views** in Unity Catalog define measures and dimensions once, on top of the star schema, so dashboards, Genie spaces and SQL users share one definition of "revenue".

## Deploying it: Databricks Asset Bundles

This repository includes `databricks.yml`, an Asset Bundle that deploys the notebooks as a job, with the star schema and vault branches running in parallel, and the SQL file as a pipeline:

```sh
databricks bundle validate
databricks bundle deploy -t dev --var catalog=<your_catalog>
databricks bundle run lab_notebooks -t dev
```

Bundles put jobs, pipelines and their configuration in Git, with `dev` and `prod` targets, which is the basis for CI/CD ([chapter 8](08-implementation-guide.md)).
